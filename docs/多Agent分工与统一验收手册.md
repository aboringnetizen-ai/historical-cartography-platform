# 历史地理考证与历史地图制图平台

## 多 Agent 分工、协作和统一验收手册

本手册用于安排两位后端 AI、Gemini 和 Claude 的开发，约定代码归属、交接接口、验收证据与跨会话恢复。产品范围、冻结字段和硬门禁以 [SPEC v4.0](https://docs.google.com/document/d/1pT0K3gbotZX9EasapG4wbJ5LamzTw2QgvxuJ7JDkk6g/edit?usp=sharing) 第 1、9、10、11、12 节为准。本文的任务编号、状态和模板用于协作。

**启动状态** · Phase 0 基线已固定，干净检出通过类型检查与 4 项纪年测试。可由 [架构状态](architecture-state.json) 取得基线 SHA，由[服务契约交接](服务契约交接.md)取得编译过的地图和证据样例。各包实施进度和验收结果以架构状态为准。

**参考素材** · [江山时序](https://github.com/DeanChensj/jiangshan-map) 用于对照历史地图交互和数据组织。用户提供的 [B 站链接](https://b23.tv/ayPqKcI) 与截图用于对照地图、时间轴和导播风格。引用数据、代码和素材时逐项记录来源及复用条件。历史事件和疆域仍按 SPEC 的证据规则验收。当前只确认了 B 站链接对应的视频页，画面验收可先用已提供的截图。

### 1.1 工作区与集成方式

1. Codex 先形成可检出的基线提交，记下完整 SHA 和实际集成分支。各角色从同一基线创建自己的分支，分支可用 `backend/core`、`backend/scholar`、`frontend/studio`、`frontend/review-<任务号>`。共用机器时使用不同 worktree；独立环境按同一 SHA 检出。各环境都用锁文件安装依赖。
2. 开工前核对当前目录、分支、工作区状态、包归属和依赖任务。记录本任务的写入路径。根配置、共享类型、公共 API 和 CI 的变更先让 Codex 与受影响的调用方确认；确认结果与差异一起交接。
3. 并行任务在自己的分支上提交可审查的变更。Codex 在集成分支上按依赖合入，并在合入后的实际代码上复跑受影响的端到端验收。只有该次运行对应的提交可以记为已验收。没有共享远端时，可以交接补丁及其基线 SHA，通过双方可访问的位置传递。
4. 对剩余工作按任务实际状态记录。外部依赖或权限卡住时，标出阻塞的具体用例、已尝试的恢复办法和可以独立推进的任务。产品和史学裁决由用户处理，代码上的可逆实现细节由包负责人处理。

## 4. 统一硬门禁

| 门禁 | 执行点和主责 | 通过条件 | 拦截验证 |
| --- | --- | --- | --- |
| **G1 拓扑与古地理** | Codex · 建模与提交事务 | 同纪元共享弧段接壤误差为 0，零自相交、零非声明重叠、零异常碎面。声明吸附到某时代自然要素的弧段与对应参考线段 Hausdorff 距离为 0。 | 断裂、重叠、非预期碎面和错时代吸附均拒绝。相同空间在不同纪元的边界彼此隔离。 |

| **G2 事件绑定** | Codex · 打开变更与最终提交 | `bound_event_ids` 至少有一个合法事件，受影响弧段和面有相应 `driven_by_event_ids`，变更与事件在同一事务约束下持久化。 | 空绑定、无效事件或变更实体漏绑时拒绝。核验失败后检查持久化状态。 |
| **G3 信源与原文** | 后端二产出核验，Codex 在提交事务内执行 | 拒绝级来源拦截；引文在指定索引版本、页码和 OCR 行号或网页存档定位可核对，分级符合正式定稿规则。 | 构造同一句出现在别页、引文伪造、索引未就绪、撤换证据版本与仅 T3 的案例。T3 线索进入 `PENDING_T1_VERIFICATION` 和溯源流程；T2 只作合规的临时参考。 |
| **G4 人工锁和学术分歧** | Codex · 提交事务，后端二提供冲突证据 | 已锁实体得到保护，T1 分歧保留双方证据并转人工裁决。正式变更关联经过审核的版本。 | AI 改锁定实体、审核后证据变化、T1 分歧未裁决，都拦截正式写入。候选可在相应待审流程保留。 |
| **G5 标注与确定性** | Gemini 提供布局和帧就绪，Codex 在提交相关预览与导出路径执行，Claude 复核视觉 | 约定视图中的高优先级地名碰撞数为 0。每帧通过 `map_idle + fonts_loaded + shaders_ready`，并校验瓦片完整与 9:16 HUD 安全区。 | 模拟瓦片、字体或 Shader 未就绪与超时，制造高优先级文字碰撞和 HUD 遮挡，确认报告定位并阻止对应提交或产物发布。 |

自动报告至少能定位到门禁编号、失败原因和受影响对象。例如拓扑问题定位到纪元和弧段，证据问题定位到事件、来源版本和页行，视频问题定位到帧和 HUD。提交走后端真实事务，渲染走真实逐帧检查。视觉审阅以固定变更版本的 Before/After 为据；输入、几何或依赖证据更换后复查受影响的项目。

开新会话、压缩上下文或换 Agent 时，先读入口、红线与架构状态，再只加载当前任务卡、相关 SPEC 小节、接口与测试。可用代码和证据链接找回细节，平时不需要在每个会话反复贴整份规格。仓库中找不到的旧会话结论先查实际差异、提交或验收记录；无证据则记为待核实。

Google 文档需要有访问权限的账号。若某个 Agent 无法读取，协调者可以提供经用户允许共享的相关章节摘录，附规格版本和章节编号。先依据仓库里的契约、门禁和验收样例开展范围已明确的工作。涉及冻结字段解释、证据采信或历史裁决的疑问登记到任务卡，等能够核对原文后关闭。

### 6.2 恢复步骤

1. 核对目录与改动。运行 `git status --short` 和 `git branch --show-current`。已有提交时再运行 `git rev-parse HEAD`，并与任务卡的基线比对。保留原工作树改动。
2. 确认任务编号、负责人、依赖是否到位、允许写入的路径以及本任务会碰到的门禁。读任务最后一次交接中的提交、失败用例和恢复命令。
3. 从代码和测试还原事实。重新打开目标函数、Schema、失败输出以及最近的可重跑样例；输入或提交已改变时复跑受影响测试。状态显示已通过而缺少对应版本证据时记为待复验。
4. 完成一个可验证的工作切片。优先补一个实际入口或用例，保留其复现命令和结果，再推进下一块。
5. 在转交、上下文将压缩、会话中断或依赖变化前，写下固定提交和工作树状态、已做与未做、遗留问题、真实测试结果和第一条恢复命令。若工作尚未提交，标明未提交的文件位置或补丁，并指出怎样保留它们。
6. 接收者从交接所指版本复跑最小用例。Codex 在实际集成后刷新架构状态和证据指针。旧结果在新版本需要复跑时，保留为历史记录。

把任务切成可独立验收的小段。比如把 `C-03` 拆成「打开并关联事件」「一次微单元移交」「提交与重试」「回滚」四段。每段交接只携带实际改动涉及的路径、入口、例子、门禁和恢复步骤。合并后的验收仍按原任务编号收齐，避免各子段各自通过但联合流程失效。

### 6.3 状态推进与变更记录

| 状态 | 何时使用 |
| --- | --- |
| `planned` | 已安排，依赖、任务卡或基线仍待准备。 |
| `in_progress` | 有负责人和实际工作。记录最近的可复现成果。 |
| `review` | 已给出可审查提交或补丁以及验收证据；等待消费方复验或整合。 |
| `blocked` | 有明确阻塞条件，注明影响、已试方法和解除后第一步；独立任务继续推进。 |
| `accepted` | 在集成提交上满足本任务验收，证据可复查，并已更新状态。 |

发现规格歧义时，记录章节、原字段、两种解释、影响的生产方与调用方、最小验证办法。先继续不依赖该歧义的工作；需要修改冻结契约、产品范围或史学结论时，由对应负责人和用户裁定。决定写入仓库引用，并标明生效提交及需要重跑的用例，确保各 Agent 从同一版本恢复。

| 恢复时发现的问题 | 处理方式 |
| --- | --- |
| 上一会话说已通过，实际记录来自另一个提交 | 找到对应提交、输入与报告，复跑当前版本的最小用例，再更新状态。 |

| 只能拿到源码补丁，没有上个环境 | 从指定基线核对并应用补丁，用锁文件重建环境。依赖真实 OCR、数据库或渲染资源的用例，使用交接样本与生产路径重新执行。 |
